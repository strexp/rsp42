# Operations

## Build and run

```sh
make build
cp config/config.example.yaml config/config.yaml
./bin/rsp42 smdpp --config config/config.yaml   # SM-DP+
./bin/rsp42 smds  --config config/config.yaml   # SM-DS
```

## Databases

**SQLite only** (pure Go driver), migrated automatically at startup via goose.
PostgreSQL/MySQL and any other backend are explicitly not supported:
`profiles.repository` accepts only `sqlite`, and any other value fails
configuration validation with an explanatory error. The
schema is versioned migrations under `internal/store/migrations/`. Separate DSNs
for the SM-DP+ (`profiles.store.dsn` → `db/rsp42-smdpp.db`) and SM-DS
(`smds.store.dsn` → `db/rsp42-smds.db`); the parent directory is created on
startup. Apply migrations manually with `rsp42 admin migrate [--db dp|ds|all]`
(the default, `all`, covers both roles).

Sensitive columns (`cc_hash`, `server_challenge`, `smdp_ot_sk`,
`shared_secret`) are encrypted with AES-256-GCM using the KMS key-encryption key.
The KEK is given either as `kms.kek_hex` (64 hex characters) or via the file
`kms.kek_file` (exactly 32 bytes); it must be protected and backed up, and it is
required to read any persisted session material. Rotate it with
`rsp42 admin rekey --new-kek NEW`.

## Certificates

Default material is the SGP.26 v3.0.2 Variant O test set under `testdata/sgp26`
(generated by `scripts/extract-testdata.sh`, invoked via `make testdata`).
Startup validates the chain, role/policy OIDs, key usage, SAN OIDs/DNS and
validity for the configured curve. The test DPtls/DStls certificates are valid
until 2027-03; `certs.allow_expired_test_certs` downgrades expiry to a warning
(test only).

`rsp42 smdpp` uses `CERT.DPauth`/`CERT.DPpb` for signatures and `CERT.DP.TLS`
for TLS. `rsp42 smds` uses `CERT.DSauth` and `CERT.DS.TLS`. ES2+/ES12/ES15 use
mutual TLS; ES9+/ES11 use server-authenticated TLS.

## Container image

The multi-stage `Dockerfile` produces an `alpine` runtime image. It preinstalls
the **dn42 root CA** (`deploy/dn42-root-ca.crt`, from
<https://wiki.dn42/services/ca/Certificate-Authority/>) so outbound TLS to
`*.dn42` services validates, and bundles `config.example.yaml` at
`/etc/rsp42/config.example.yaml`.

```sh
docker build -t rsp42 .
# the role is selected by RSP42_ROLE (there is no default role)
docker run -e RSP42_ROLE=smdpp -v $PWD/config/config.yaml:/etc/rsp42/config.yaml rsp42
docker run -e RSP42_ROLE=smds  -v $PWD/config/config.yaml:/etc/rsp42/config.yaml rsp42
```

## Health and shutdown

`/healthz` and `/readyz` on the admin port. SIGINT/SIGTERM trigger a graceful
shutdown (15s grace). Request bodies are capped (1 MiB control plane, 4 MiB
ES9+).

## CORS

The LPA-facing and admin listeners send no CORS headers by default, so a browser
page served from another origin cannot call them. Enable it per process:

```yaml
smdpp:            # or smds for the SM-DS
  server:
    cors:
      allowed_origins: ["https://ops.example.com"]   # or ["*"] (dev only)
```

An empty list disables CORS. `deploy/demo.html` is a single-file front-end for
the management API; serve it from an origin listed here (or use `["*"]` in a
test config).

## UPP templates

UPP templates live in the `upp_templates` table and are selected by the eUICC's
advertised SAIP version. There is no `upp_dir` in the config: the SM-DP+ never
reads the filesystem at request time, and templates are seeded explicitly by the
CLI (hot-updatable via the registry):

```sh
rsp42 admin upp import --dir testdata/upp
rsp42 admin upp list
```

`profiles.default_upp` optionally pins a registry template name used when the
eUICC's profile version does not select one.

## Personalization

Per-ICCID personalization values live in the `personalization` table (K/OPc
encrypted at rest with the KMS key-encryption key). There is no personalization
source in the config; seed/refresh explicitly:

```sh
rsp42 admin personalization import --file testdata/personalization/profiles.csv
rsp42 admin personalization list
rsp42 admin personalization delete --iccid X
```

Resolving by ICCID replaced the previous single global cursor, which was not
safe under concurrent downloads. If a profile has no personalization record, the
order's ICCID is still written into the profile (the operator can supply the rest
later).

## Administrative tasks

```sh
rsp42 admin profile list|show        # inventory (not users)
rsp42 admin session gc               # remove expired sessions
rsp42 admin gc [--keep 720h]         # delete stale notifications/orders/audit
rsp42 admin iccid import|list|stats [--start X --end Y]   # manage the ICCID pool
rsp42 admin upp import --dir DIR     # import UPP templates into the registry
rsp42 admin upp list                 # list registry templates (SAIP version, hash)
rsp42 admin personalization import --file CSV|list|delete   # manage per-ICCID personalization
rsp42 admin activation-code --fqdn F --matching-id M [--qr out.png]
rsp42 admin smds event list|delete
rsp42 admin es2p downloadOrder|confirmOrder|cancelOrder|releaseProfile
rsp42 admin mock-operator            # test-only operator stub
```

## Known limitations

Online CRL/OCSP is out of scope (expiry is validated, revocation is not). Both
the JSON binding (§6.5) and the ASN.1 binding (§6.6) are implemented for ES9+ and
ES11; ES2+/ES12/ES15 use the JSON binding only, as the specification mandates.
Only NIST P-256 is supported (`certs.curve: brainpool` is not implemented).

Explicit non-goals (decided, not pending — see
`docs/esim42-integration-gaps.md` §8.4): PostgreSQL/other database backends,
multi-replica deployment, per-carrier ES2+ client certificates (tenant
attribution uses `functionRequesterIdentifier`), and rsp42-side rate limiting /
429 semantics. See `docs/coverage.md` for the full list.

Multiple SGP.26 certificate variants can be served by one deployment by listing
additional certificate sets under `certs.identities`; the identity whose CI the
eUICC proposes is selected automatically. `profiles.ppr_ids` populates the
Profile Policy Rules (the ES2+ DownloadOrder body cannot override them, C1), and
the UPP template is selected from
the eUICC's advertised profile version unless the order (or the tenant default)
pins one.

## Observability

`GET /metrics` on the admin listener exposes Prometheus text metrics:
download-progress notifications by tenant/point/status, session and ICCID
reservation GC counters, ICCID pool depth by state, and the outbound ES2+
callback queue depth. ES12 registration failures are counted and audited, as are
outbound `ES2+.HandleAcrRequest` confirmations
(`rsp42_acr_requests_total{tenant,outcome}`).

All SQLite transactions run in IMMEDIATE mode, so the read-then-update paths
(ICCID reservation, idempotency claim) cannot deadlock on a lock upgrade. The
database is still single-writer: **exactly one rsp42 process per database file**.

Multi-replica deployments (leader election, distributed locks, shared storage)
are explicitly **not** supported and are not planned. Scaling out means
re-architecting, not adding a lock: see
`docs/esim42-integration-gaps.md` §8.4. For the same reason rsp42 does not
implement request rate limiting (no 429 semantics) — throttling belongs in the
operator backend in front of it; rsp42 enforces only resource-level quotas
(`tenants.template_quota`, `tenants.profile_quota`).
